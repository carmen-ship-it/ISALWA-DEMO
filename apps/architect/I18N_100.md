# Architect i18n — status report

**Mission:** route Architect's client-facing UI through a real i18n system, Spanish as the
default/client locale, English keys as source of truth. Migrate hardcoded English *and*
hardcoded Spanish literals into that system, not just one or the other.

## What shipped

### 1. New i18n system — `apps/architect/lib/i18n/`

No i18n framework existed anywhere in the monorepo (`apps/architect`, `apps/api`, `apps/web`,
`packages/*`) — no `next-intl`, `react-i18next`, `messages/*.json`, nothing. This mission
introduces the lightest system that fits Next.js 15 App Router with both server and client
components, and Architect's "Spanish first" reality:

| File | Purpose |
| --- | --- |
| `lib/i18n/config.ts` | `LOCALES`, `DEFAULT_LOCALE` (`"es"`), `isLocale()` |
| `lib/i18n/translate.ts` | `MessageTree` type, dot-path `lookup()`, `{token}` `interpolate()`, `translate(locale, key, params)` with fallback-to-default-locale then fallback-to-key (never crashes, logs a dev warning) |
| `lib/i18n/context.tsx` | `LocaleProvider` (React context) + `useTranslations()` hook for client components. **Works without a provider** — falls back to `DEFAULT_LOCALE` — so no big-bang provider wrap was required to start migrating components |
| `lib/i18n/index.ts` | Barrel export + `t(key, params)` — a server-safe translation function for server components / plain modules that can't call hooks |
| `lib/i18n/messages/es.ts` | Spanish dictionary — ~870 lines, source of truth for client-visible copy today |
| `lib/i18n/messages/en.ts` | English dictionary — mirrors every `es.ts` key |

Usage:
- Client components: `const { t } = useTranslations();`
- Server components / helpers outside React: `import { t } from "@/lib/i18n";`
- Keys are dot-paths namespaced by component, e.g. `t("businessKnowledge.saveNotes")`.
- Interpolation: `t("key", { name: "Foo" })` replaces `{name}` in the template.

No provider is currently mounted in `app/layout.tsx` — Architect only serves Spanish to
clients today, so `useTranslations()`'s built-in `DEFAULT_LOCALE` fallback *is* the active
behavior. Wiring a `LocaleProvider` + a locale switcher is a follow-up, not a blocker: every
migrated string already resolves through `translate()`, so flipping the default locale or
adding a switcher later is a config change, not a re-migration.

## Honest gaps — not migrated in this pass

Being explicit rather than claiming false 100%. Ordered roughly by client visibility:

### A. Guided discovery interview flow — **highest-value remaining gap**
`components/discovery/guided/*` (`guided-assessment.tsx` 472 lines, `review-panel.tsx` 253,
`answering-panel.tsx` 146, `stage-brief.tsx` 129, `finish-panel.tsx` 80, `stage-stepper.tsx` 66)
plus `components/discovery/living-whiteboard.tsx` (114) and `opportunity-list.tsx` (57). This is
the actual interview experience (~1,435 lines) — same priority tier as the report, but the
report was completed first because it's the artifact clients keep. **This should be the very
next target.**

### B. Remaining workspace panels
- `components/workspace/brand-settings-panel.tsx` (444 lines) — brand/terminology admin config
- `components/workspace/brand-experience-panel.tsx` (497 lines)
- `components/workspace/executive-simulator-panel.tsx` (603 lines) — "what-if" scenario tool
- `components/workspace/deliverables-panel.tsx` (616 lines)

These are all still 100% hardcoded Spanish literals (pre-existing "Spanish normalize" state,
per the constraint not to undo that work) — functionally fine for a Spanish-only client base,
but not yet routed through `t()`.

### C. Presentation label layer — `lib/presentation/executive-language.ts` and siblings
Functions like `priorityLabelEs()`, `roiBandLabelEs()`, `riskLevelLabel()`,
`strengthBandLabelEs()`, `moduleLabel()`, `phaseLabel()`, `coverageBandLabelEs()`, etc. are
called from nearly every migrated component in this mission (left as-is intentionally — they
map consulting-engine enum values, e.g. `"critical"` → `"Crítico"`, to display labels, and are
core business logic, not view templates). They currently return hardcoded Spanish directly
instead of resolving through `lib/i18n`. Wiring these through `t()` is the highest-leverage
follow-up because a single change here would flip labels across dozens of already-migrated
call sites — but it's a deliberately separate, careful mission: these functions are consumed
by both UI and (potentially) non-UI derivations, so the refactor needs its own test pass.

### D. Consulting-engine internals (intentionally out of scope)
IDs and internal enum values in `lib/blueprint`, `lib/solution`, `lib/process-visualization`,
`lib/history`, etc. (e.g. `"Sales"`, `"critical"`, `"designed"`) stay in English by design —
per the mission brief, these are consulting engine identifiers, and presentation already
resolves them to Spanish via the `*Label()` functions in gap C above. They never render
directly to a client.

### E. Small residual items
- `app/layout.tsx` — `<title>` / meta `description` are plain string literals (Next.js
  `Metadata` export, not a React tree `t()` can run inside without extra plumbing).
- `lib/auth` — `signInAction`'s error strings (e.g. invalid credentials) were not audited in
  this pass; `LoginForm` renders whatever `result.error` contains, but that string's source
  (inside `lib/auth`) was not migrated to `t()` in this mission.
- Some literal Spanish inside data-shaped constant maps that were left as maps rather than
  migrated key-by-key when the map was very large and low-traffic (none found large enough to
  skip in this pass — all maps encountered were folded into `es.ts`/`en.ts`).
