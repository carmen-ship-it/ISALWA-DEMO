## Remaining gaps

1. **No inbound path.** Reopen-on-inbound is a tested rule with no caller. Until WhatsApp (or another inbound source) exists, `Esperando al cliente` and `Resuelta` change only by hand.
2. **No automation exists**, so "human takeover pauses replies" is a recorded fact, not an enforced one. There is no resume command and no AI state values.
3. **Release / reassign.** Still no way to release a held conversation or for a manager to reassign it; a held conversation can only change state by its holder or a manager. A conversation held by someone who is suspended has no release path (manager can still change its state). Needs an authority decision.
4. **UI shows transitions by state and holder only**; whether the viewer may act on *someone else's* held conversation is decided by the server, so those buttons can answer "NOT_HOLDER" (shown as a clear message). The holder's name is not in that message because the error envelope has no details for this route.
5. Notes: no edit/delete/pin by design (append-only), no mentions or notifications, no search over notes, no attachments. Notes load per conversation on first open (no live refresh).
6. State changes do not notify anyone and do not create commitments; the status history is stored but has no reader UI yet.
7. Relationship-end previews / queued-recipient invalidation and recycled-number history (Batch 5 gap 4) still wait for outbound intents.
8. Not browser-verified; not independently reviewed; no provider, hosting or push.
